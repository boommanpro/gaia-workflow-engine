摘要 · TL;DR

先给结论。这套引擎的骨架是「事件与传输彻底解耦」：引擎只管往事件总线发事件，谁订阅、几个窗口订阅、断没断线都不关它的事——这让多窗口、断线重连、崩溃恢复、轨迹回放都变成同一套数据的不同视图。

整体判断

换核到 AgentScope Java 之后，ReAct 循环、模型重试、run 内压缩交给了框架；自研部分收敛到四件真正有差异的事：会话事件总线（关窗继续）、三账本观测（可复现落账）、实证驱动的防呆体系（RepeatToolGuard/WrapUpGuard/假成功检测）、服务端画布草稿 CAS 状态机。这四件事恰好都是 dsh / owb 没有或做得更薄的地方。

主要短板集中在工程化收尾：运行态全在单机内存、stop 对阻塞工具无效、配置面与实现漂移、前端重连无退避。都属于 P0/P1 可修，不动架构。

一句话对标

vs dsh：dsh 的「一切皆持久台账 + 纯投影」在概念纯度上仍是天花板；gaia 在服务化形态、防呆粒度、可复现落账上反超，但 steering 持久化与中断语义完整性要向它补课。

vs owb：gaia 的执行追踪页复刻了它的读侧合成与「语言诚实」原则，并补上了它没有的实时跟随；owb 的 trace 体积工程（$msgs 编号去重、滚动账本）与「target 行 / 耗时归一化条」仍值得抄。

05

防呆体系 · 弱模型对抗的实战结晶

两条防线：RepeatToolGuard（…agent.runtime.RepeatToolGuard，判定键 = 工具名 + 键排序规范化参数）管「复读与空转」；WrapUpGuard（…agent.runtime.WrapUpGuard）管「系统性失控」——两者都只软停收尾，绝不砍 run。

检测线触发条件升级动作
同参失败复读同 key 连续失败；失败链不被中间其他调用清零，仅同 key 成功清零（:93-99）INVALID_ARGS 第 2 次 → 附加提醒；第 3 次硬熔断 STOP（:102-110）。其他错误 3/5/8 次阶梯提醒
同参成功空转同参数连续成功 ≥3 次（语法成功≠语义进展）APPEND 提醒「已重复成功，请检查语义目标」（:73-86）
交替空转最近 8 个 key 出现 k1,k2,k1,k2 模式（典型：edit→run 互相甩锅，:130-146）下一次 record 带循环警报文案（:157-161）——dsh/owb 均无此检测
系统性失控WrapUpGuard：连续 N 轮「有工具调用但全失败」计 noProgressStreak；轮次≥30 或无进展≥8（:34-46）wrappedUp → invokeTool 全部 rejected + 收尾指令 advisory，让模型用手写正文收尾（:66-79）
设计取向：所有防呆都遵循「先提醒（appendGuardNote 进 tool_result payload，模型看得见）→ 再软停（收走工具）→ 从不中途杀死 run」。配合 RunWorkflow 的假成功检测（end 未达 = canceled 连坐；end 字段缺值顺 ref 点名上游），构成了 2026-10 高失败率诊断后的 P0-P3 修复闭环。

11

gaia 领先的点

八条，每条附代码证据。共同主题：不只是「有这个功能」，而是把它做成了可被测试钉死、可被多窗口共享、可被模型自修的协议。

1. 「关窗继续」的多窗口会话架构

SessionEventBus 快照 + 500 缓冲 + subscribe 只推 run_state（SessionEventBus.java:150-161）；前端 applySnapshot 重建现场。dsh/owb 都是单机单窗口会话语义——这是服务化形态带来的代际差异。

2. 可 curl 复现的 LLM 落账

RecordingModel 把每次调用还原成 OpenAI 同构请求原封不动全量落库（2026-10-11 起不再做增量压缩）；TrajectoryPanel 对历史增量行自动拼回并标注口径。排查「模型当时到底看到了什么」时，gaia 是拿日志直接重放，dsh 要在运行时重建，owb 只服务体积。

3. 实证驱动的防呆粒度

交替空转 k1,k2,k1,k2 检测、INVALID_ARGS 3 次硬熔断、run_workflow 假成功双重检测（end 未达连坐 + 字段缺值顺 ref 点名上游）——每条都带 2026-10 实测案例注释。dsh 无 turn 上限与循环检测，owb 只有同参 4 次熔断。

4. 服务端画布草稿 CAS 状态机

_meta{boundCode, baseRevision, draftRevision} 随 artifact 持久化；applyOps 两遍法（副本校验 → 部分应用 + skipped{path,issue,fix}）；staleRevision 错误码带补救指引，模型可自修。三家独有。

5. 双引擎热切换、工具层共享

AgentExecutionRouter 按 AgentDefinition.engine 路由；方舟引擎只换「谁驱动循环」，ArkEventTranslator 把远端事件翻译进同一 SSE 协议、custom_tool 回本地执行器——A/B 一个开关的事。

6. 前端性能模型被测试钉死

三重 rAF 合帧 ≈20fps + 条目 memo + 尾块 200ms 节流：长流式只有「正在生长的一条」重渲染；closed 标志收敛语义、appendLiveRow 幂等合并各有回归测试（live-timeline.render.test.tsx / session-merge.test.ts）。

7. 回放 = 线上同一条代码路径

handleEvent 是唯一分发器，SessionEventFileRecorder 的 ndjson 包一层就是前端 fixture——离线 UI 回放具备逐字节一致的可信度，且测试零 LLM 依赖（ScriptedChatModel）。

8. 三账本分账记 + 纯合成 trace

事件/LLM/工具三张表各司其职，AgentTraceService 零自建存储合成 span/generation/状态（30min stale 判中断——与 owb 同一血泪结论）。账本查询成本远低于 dsh 的全量台账扫描模型。

可优化点 · 按优先级

每条注明问题证据与可借鉴来源（借鉴 dsh/owb = 对方已有成熟做法可直接搬机制）。P0 影响正确性/可扩展性，P1 影响韧性与成本，P2 是打磨。

P0正确性与可扩展性

1. 运行态全在单机内存，多实例部署即失效

AgentSessionRunService.runs、SessionWorkflowDraftService.drafts、AskUserPendingStore.pending、SteeringInbox 全是进程内 Map；get→读改写非原子，run_workflow 读草稿与 applyOps 并发可能互相覆盖。
方向：粘性路由 + 显式所有权（借鉴 dsh SessionAlreadyOwnedError 的「写句柄进程独占」语义），或状态外移 Redis / DB。

2. stop 对阻塞型工具无效

stop() 只置 cancelled 标志，而 ask_user 阻塞 future.get(5min)、run_workflow 轮询 180s 都不检查 interrupt——用户点停止后 run 线程仍被占住；agent-session-run 还是无界 cachedThreadPool。
方向：两执行器循环内加 isInterrupted() 检查（引擎已把 interrupt 协件放进 variables）；借鉴 dsh：每个 await 点 throwIfAborted。

3. 配置面与实现漂移

AgentProperties.Compaction（triggerRatio=0.7 等）与 Spill 整组没有消费者；实际是 SessionCompactionService 硬编码 50%/6 条 + 框架 80% 双轨并存，运维照配置调参必然无效。
方向：要么接线要么删除，压缩阈值统一从配置读。

P1韧性与成本

4. SSE 重连无退避上限、无 jitter

前端 connect() 固定 1500/2000ms 无限循环（AgentContext.tsx:1212-1227）；会话被删/后端 404 时每 2s 空打一次。
借鉴 dsh：backoff 500ms ×2 → 10s 封顶 + 握手超时。

5. request_json 全量落 SQLite 单列，1M 窗口未设防

长会话单行可达 MB 级。2026-10-11 已拍板全量保真（曾实现的 seq>1 增量形态因调试口径不可信被移除）；体量大之后可再考虑 owb 的 $msgs 编号去重或滚动归档，历史增量行前端兼容读取。

6. 事件落库在热路径同步执行

ToolLogRecorder.persistEvent 每事件同步写 SQLite（单写者），document/plan 等大 payload 高频循环下是吞吐瓶颈；attachTimelineToLastAssistant 按「最后一条 assistant」定位，链接式 steering 连续两 run 可能附错行。
方向：异步批量 flush + timeline 按 runId 归属。

7. Steering 收件箱不持久

运行中排队的新消息在重启后丢失。
借鉴 dsh：inbox 变更即持久化 splice 事件（gaia 可落 agent_session_event 再折叠恢复）。

8. 前端死代码与双实现清理

MessageList.GroupedToolCard 与 chat/ToolSteps 两套工具卡并存；AgentContext.onToolResult（:1071-1090）失效双路写放大；tokenUsage.estimated 恒 0 导致 Dock 进度条不可达；activePlan 在自治模式下恒 null 的执行计划区块不可达；SessionList 删除会话无确认（与其文件头注释自相矛盾）。

9. 事件契约无编译期防护

AgentEvent.type 是自由字符串，前后端 30 种事件靠约定对齐；AgentRequest.maxTurns(@Deprecated)、SseAgentEventSink、ToolExecutionMode.FRONTEND 默认值等旧链路残留。
方向：后端枚举 + 前端 union type 从同一 schema 生成。

P2打磨

10. 压缩的 KV-cache 友好化

借鉴 dsh：摘要辅助调用重放会话真实前缀、只把压缩指令放最后一条 user 消息，复用 provider 前缀缓存而非使其失效；gaia 当前摘要独立拼 prompt，长会话下每次压缩都全价。

11. LLM 重试状态不持久

借鉴 dsh：llm/retry 意图先落盘再等待、计数从投影恢复；gaia 重启后重试计数清零，可能对同一抖动重复整轮退避。

12. 大工具结果 spill 未接

借鉴 owb spillToolResult（>2 万字落盘、上下文只留头尾+路径）/ dsh compaction-tool-result-pruner；gaia 的 AgentProperties.Spill 参数写好了却没有消费者（同 P0-3）。

13. 追踪详情页信息密度

借鉴 owb：每步 target 行（从参数自动提取动了哪个文件/跑了什么命令）、耗时按全 trace 最慢步归一化的横条、「工具耗时 vs 模型耗时 / 最慢一步」七格摘要；gaia 已有 4s 跟随（owb 没有），补上这三件就全面反超。
