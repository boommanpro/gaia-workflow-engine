问题清单

  • 比例失衡：药丸里等宽字体数字 + 一根 26px 小短棒，两件东西互相打架，看起来像调试组件而不是产品组件。
  • 低占用常驻 = 噪音：1M 窗口下日常占用 5~15%，一根 6% 的常驻条看久了等于没有（owb 源码注释原话）。真正该出现的时机（接近压缩阈值）反而没有任何升级提示。
  • 明细卡层级平：一根 5px 单色条 + 四行圆点列表，没有「分类占窗口多少、还剩多少」的一眼可读性；浮层左对齐 320px，和窄栏构图脱节。
  • 没有压缩语境：条上不解释「什么时候会压缩、压缩后会发生什么」，用户不知道该在什么时候另开会话。
  • 口径隐患：limit 兜底 32768，与真实模型窗口（1M）不一致时数字整条失真；estimated ~ 标记只有 title 提示，浮层里才有。

02对标结论：dsh / owb / 业界怎么做

三个来源指向同一个共识：容量条本身不该是常驻主角，明细才是；占用要过阈值才升级存在感。

dsh（deepseek-harness）— 统计药丸派

  • Composer 工具栏放两颗统计药丸：活动 N 轮 · 42 tok/s、用量 128.4k · 缓存 86%，点击弹出portal 对话框（上锚定、视口夹紧、Esc/外点关闭）。
  • 对话框是统一皮肤：标题行（icon + 名称 + 右对齐精确值）→ 分隔线 → dl 键值行。没有进度条，dsh 把 token 当「账本」而非「水位」。
  • 每条完成的助手回合尾部有 已消耗 12.3k 小药丸，点开单轮明细（输入/缓存读/缓存写/输出/推理/模型路由）。
  • 压缩在时间线里是一行可折叠注记：icon + 「上下文压缩」+ 「已将 N 条 / X tokens 压成摘要」，展开看摘要正文。

owb（openworkbuddy）— 安静水位线派

  • 输入框正上方一根 90×4px 迷你条 + 上下文 87%（120k / 200k） 灰字。
  • 默认隐藏：占用 < 45% 完全不渲染（源码注释：日常挂一根 12% 的条等于没有）。
  • 过压缩阈值（60%）变色 + 换文案：「下一轮开跑前会自动压一次，想留全文就另开会话」——条上的线就是后端真会触发压缩的那条线。
  • 压缩过程「开始/结束共用一行、只报等待秒数」，明确不画假进度条；单轮用量收在回复操作条的小字 + hover tooltip。

业界惯例（Claude Code / Cursor / Cline）

  • Claude Code：状态行常驻低调数字 161.3k / 200.0k tokens (81%)；/context 打开按类目分块的占用图（系统提示词 / 工具 / 消息 / 空闲），接近上限时颜色升级并提示 auto-compact。
  • Cursor：composer 内联「用量 / 窗口 (百分比)」读数，点开明细；Cline：任务头部一根带百分比的进度条 + 阈值 auto-compact，其 issue 区大量吐槽「前端估算与 API 口径不一致」——数字必须来自后端真账本是公认教训。
  • 共识公式：百分比 + 绝对值双色阶（正常→警告→危险）+ 点击展开分类明细 + 压缩触发点明示。

03方案 A · 统计药丸 + 过阈值容量告警推荐

dsh 的形态 + owb 的显隐哲学：工具栏平时只有「用量」一颗安静药丸（token 是账本，不是水位）； 占用跨过压缩阈值后，第二颗「容量」药丸才出现并随危险度升级。明细一律点开统一的对话框皮肤。

方案 A 规格要点

  • 用量药丸（常驻，有账目才渲染）：icon + 用量 128.4k · 缓存 86%；点击弹「会话用量」账本（缓存命中 / 输入未命中 / 缓存读 / 缓存写 / 输出，右栏精确值）。整段口径取自 agent_llm_call_log 全会话聚合，与压缩决策无关、不受压缩影响。
  • 容量药丸（条件渲染）：占用 ≥ 60%（= 后端压缩阈值）才出现；60–80% 灰字、80–92% 警告色、≥92% 危险色；点击弹「上下文容量」卡（分段条 + 分类占比 + 压缩提示文案）。比例色阶沿用现状三档语义。
  • 单轮用量：每条完成的助手回合尾部挂 已消耗 12.3k · 缓存 91% 小字，点开单轮账本（需后端新增按 turn 聚合的小接口，数据已在 llm_call_log 里）。
  • 压缩注记：沿用现有 compaction 系统注记的数据，统一成 dsh CompactionItem 皮肤（icon + 标题 + 一行摘要 + 可展开正文）。
  • 所有弹窗走统一 stat-dialog 皮肤：上锚定 portal、视口夹紧、Esc / 点外关闭、淡入动画。

04方案 B · owb 式安静水位条

方案 B 规格要点

  • 条体：12px 灰字 + 96×4px 圆角轨道；显示线 = max(30%, 压缩阈值 − 15%)，压缩阈值由后端随 context-stats 一并下发（后端把真触发线播给 UI，前端不算数）。
  • 过阈值：整条转警告色，文案从数字切换为行动提示；自动压缩关闭时换成「将达到窗口上限，历史最旧内容将被丢弃」一类如实描述。
  • 点击任意处弹出与方案 A 相同的「上下文容量」明细卡（分段条版）。
  • 无单轮用量、无会话账本药丸——「钱花哪了」要去 Trajectory 看。最安静，信息也最少。

方案 C 规格要点

  • 药丸内嵌 22×8px 迷你分段图 + 百分比，常驻（不分阈值）；明细卡 440px 宽，分段条加高到 10px，段间留 2px 间隙，含「空闲」段。
  • 颜色语义与现状一致：系统提示词绿 / 工具橙 / 消息黑（accent）/ 其他浅灰 / 空闲轨道色，跨方案统一，形成分类色记忆。

  • 优点：一眼全貌、最好看；缺点：1M 窗口日常 96% 空闲时分段条近乎纯轨道色，常驻的信息量低、视觉重量最高。

推荐：方案 A 为主体，吸收 B 的显隐哲学，C 的分段条只活在弹窗里

  • gaia 对话层视觉基调本来就是 dsh（窄栏、折叠、系统注记卡），药丸 + stat-dialog 是同一套语言，不会突兀。
  • 产品约束是 1M 窗口 + 阈值压缩：低占用水位条/分段图是纯噪音，「过阈值才出现、越线就升级」（A 容量药丸 / B 显隐）才是对的时机模型。
  • 分段条信息密度高，但那是「点开才看」的信息——放进弹窗（A/C 共用同一张明细卡皮肤）而不是常驻。
  • 单轮用量下放到消息流（A）承接了 owb 「回复操作条小字」的角色，回答「这轮花了多少」，比任何常驻条都更贴近用户的真实疑问。
  • 若你更想要「输入框上方有一根可见的条」的安全感 → 选 B；若你想让容量成为面板主角、不在乎低占用噪音 → 选 C。

实施清单（无论选哪套，公共部分相同）

  • 前端：重写 ContextCapacity.tsx → StatsPills.tsx（UsagePill / CapacityPill 条件渲染）+ 抽取统一 stat-dialog（portal 上锚定 / Esc / 外点关闭）；ChatMessageList.tsx 回合尾部加单轮用量 meta；compaction 注记卡统一 dsh 皮肤；删除 strip 死代码形态。
  • 后端：/agent/metrics/sessions/…/context-stats 增加 compactThreshold 字段（与压缩决策同一来源）；新增按 turn 聚合的单轮用量小接口（数据已在 agent_llm_call_log）；核对 tokenUsage.limit 口径（当前兜底 32768 与真实模型窗口不一致的风险）。
  • 口径纪律（业界教训）：所有数字必须来自后端真账本；估算值标 ~ 并在弹窗内明示「以最近一次真实调用为准」；避免 Cline 式「UI 50% vs API 口径不一」的信任崩塌。
  • 验证：明暗双主题、窄栏 748px 与侧栏形态、超长会话（压缩前后）三种数据态各过一遍视觉验收。
