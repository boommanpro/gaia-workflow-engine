总体架构

三张总体架构图（交互式）+ 架构风格逐项对比。

3.1 gaia：Spring Boot 单体 + AgentScope 换核

gaia 总体架构architecture · 交互式

要点：Maven 三模块——gaia-workflow-base（43 类，自研 DSL 引擎内核 Chain/SpEL/事件）· gaia-workflow-infra（141 类，MyBatis-Plus 19 表 + 15 种节点解析器）· gaia-workflow-app（149 类，agent 运行时 + 19 控制器约 90 端点）。引擎策略接口 AgentExecutionEngine 走 Spring 注入顺序路由（AgentExecutionRouter.java:55-62），本地 AgentScope 与方舟托管共用同一 ToolExecutorRegistry。

3.2 dsh：everything-is-a-plugin 的 Cordis 插件树

dsh 总体架构architecture · 交互式

要点：319 个 workspace 包按域分组（core/llm/compaction/shell/fs/session/interaction/subagent/api/host/client/bundle/boot…），依赖方向强制 harness 包对 cordis 只放 peerDependencies（AGENTS.md:130）；客户端本身也是一棵跑在浏览器里的 Cordis 插件树，由 Host 注入 window.__DSH_BOOT__ 模块表两段式启动。

3.3 owb：Electron 壳 + Express 单体 + 原生 JS 前端

owb 总体架构architecture · 交互式

要点：server.js 9,412 行 Express 单体 + src/ 七层架构（platform→core→domains→agent/engines→server→im/cli/desktop），层间只许 require 同层或更低层，由 test/layers.js 用语法树强制；桌面壳把服务挪进 utilityProcess 子进程隔离（server-host.js:5-13），主进程 p99 显著下降。

04

Agent 运行循环

三方「一步」是怎么走的：gaia 把循环外包给 AgentScope、自己管工具管道与账本；dsh 与 owb 自研循环但事件模型截然不同（dsh 先落事件再驱动 UI，owb 步循环 + 判断闸）。

4.1 gaia：一次 run 的全链路时序

gaia 一次 run 全链路（受理 → ReAct → 三账本 → 收尾裁定）sequence · 交互式

循环本体在 AgentScope HarnessAgent：gaia 负责 run 编排（AgentSessionRunService.java:330-457）、装配（模型/提示词/护栏，AgentScopeExecutionEngine.java:151-241）、事件翻译（:704-762）与三账本落库。关键自研点：RecordingModel 装饰 Model.stream() 才能看到真实请求（框架 MODEL_CALL_* 事件不带请求内容，RecordingModel.java:22-29）。

4.2 dsh：turn/step 流转与恢复路径

dsh ReactLoopAgent 相位流转workflow · 交互式

主循环 kick() → while(await turn())（agent-loop/src/agent.ts:252-265），每步 preStep（claim inbox → 组装提示词 → agent/pre-step waterfall）→ step（prepareRequest → 流式消费 → 结算 assistant/message → executeToolCalls）。turn 结束原因五态：blocked | completed | max-tokens | aborted | error（agent.ts:318-385）。

4.3 owb：runTask 主循环

owb runTask：引擎分岔 → 步循环 → 闸口 → 交付workflow · 交互式

外层自动续跑 ≤20 轮 × 内层 max_steps=25（agent.js:3340-3342）；每步：停机检查 → 插队消息注入 → deadline/token 闸（80% 提醒）→ compactHistory → 流式调用。系统提示词拆「稳定段 + 易变段」两段拼，打 Anthropic 缓存断点（agent.js:3056-3062）。

5.1 gaia：AI 草稿生命周期（韧性之外的交付安全）

差异化结论与对 gaia 的启示

每家的领先点、跟随点与短板，以及对 gaia 下一步最有杠杆的参照。

gaia

领先点

  • 工作流画布 + DSL 校验-反馈闭环（fatal 带可抄 JSON / skeletonExample / run 回执点名上游）——三家中独有
  • 交付语义：AI 只交草稿、用户显式落版 + 假绿裁定 + CAS
  • 上下文容量观测（context-stats 四类分摊 + 缓存命中率 + 双轨压缩可视化）
  • 护栏密度：RepeatToolGuard 交替循环指纹、WrapUpGuard 收工具不砍 run
  • 双引擎共享工具层（本地 AgentScope / 方舟托管零成本切换）

短板

  • 运行态单机内存（多实例 P0）、无并行工具、无进程级沙箱
  • 可观测数据靠轮询（Trajectory 4s），非投影/推送
  • 评测仍是脚本层，缺 baseline 回归自动化
dsh

领先点

  • 日志即真相：61 种 durable 事件，UI/重试/审批/压缩全可复现可回放
  • 韧性包件化：llm-retry（durable 计数 + Retry-After）、compaction（overflow 自愈 + 图片卸载）、timeout-policy、repeat-reminder 各自独立成包
  • 工程密度：319 包 + 100% 覆盖门禁 + 三语文档门禁 + 性能预算
  • 子代理 5 provider + 沙箱（Landlock/ACL）+ 审批 fail-closed

相对弱处

  • 面向开发者而非业务场景；无模型管理面板/健康账本；developer preview 破坏性变更频繁
owb

领先点

  • 模型管理闭环：渠道/条目两层 + 5 协议 + thinking 厂商映射 + 测活 + 健康账本 + 媒体熔断（gaia 批 C 蓝本）
  • 文件交付验收 + 计费配额 + 批量报价
  • 专家团递归委派（继承 runToken/deadline/llmOverride，trace 树与界面一致）
  • 判断模型 Jev 驱动四道闸（ask/continue/memory/skill）——把「要不要问人/要不要续跑」显式化
  • 零框架工程（运行时依赖 13 个）+ 七层架构 AST 强制

相对弱处

  • server.js 9,412 行单体；无 schema 校验层；无进程沙箱（Windows SB 除外）
